# ML training and evaluation review — 2026-10-12

Static source review refreshed on 2026-10-14 against the active `nexus-ml` files. No training was run, no model artifact was loaded, and no weights/data were changed. These findings are not a trading-performance assessment. The former workspace write restriction cited in the original note no longer applies; regression tests can be added after the specific remediation design is approved.

## Findings

### ML-01 — training target was aligned to the current bar, while model contract says next-bar direction

- **Priority:** P1 (label/feature temporal integrity).
- **Evidence (rechecked 2026-10-14):** `services/nexus_ml/main.py` calculates `label = 1 if close > prev_close else 0` using the current feature event's close and the previous close seen by the process, then stores that label beside `numeric_features` from the same event. `XGBoostDirectionModel` documents its target as next-bar direction. The feature producer builds a cache payload timestamp from `datetime.now()` and emits `FeatureEvent` without a bar timestamp in its `features`; the event envelope's `timestamp` also defaults to UTC wall-clock time. Thus ML's stored `raw.timestamp` is an ingestion/publication time, not the source OHLCV bar time needed for strict chronological alignment. The fallback to a fresh `datetime.now()` applies only if both timestamps are absent.
- **Why it matters:** Training examples therefore label the same event/bar represented by the feature row, not the subsequent bar specified by the model contract. The target also depends on the last *processed* close held only in process memory; on restart the first row is labeled zero (`prev_close` defaults to current close), and skipped/delayed events can make the comparison span more than one bar. Current OHLC features include the current close. Exact leakage magnitude depends on the feature set and event timing and has not been measured.
- **Confidence:** High that target/time alignment differs from the stated next-bar contract; impact on live decisions is not yet measured.
- **Resolution (2026-10-14): Fixed and verified.** `FeatureEvent` now carries the source OHLCV bar timestamp; ML stores one pending observation per symbol/timeframe in Redis and resolves the preceding feature row only when a strictly later close arrives. Duplicate/older timestamps are ignored; pending write and completed-history append use one Redis transaction. Correctly labelled records use the versioned `nexus:features:history:v2:<symbol>` key, and both ML training readers use only v2; legacy same-bar-labelled history is left untouched and excluded from training. The first/unpaired row is not emitted. Tests cover next-close alignment, duplicate/out-of-order rejection, restart-state serialization, and training-reader version selection. Targeted ML tests: **21 passed**; full Python suite: **312 passed**, 2 existing deprecation warnings. No live Redis, model training, or artifact load was used, so the Redis transaction was verified through code review and unit-level tests, not a live integration test.

### ML-02 — outer walk-forward validation windows were not evaluated

- **Priority:** P1 (evaluation validity).
- **Evidence before remediation:** `train_all_models` constructed `X_val/y_val` only for the minimum-row check; validation predictions were not scored. Internal model CV metrics were therefore the only reported supervised metrics.
- **Why it matters:** Fold results are labeled with outer train/validation date windows, but reported model metrics are inner training-window CV metrics, not performance on those outer forward windows. Users/automation can interpret these as walk-forward out-of-sample validation when they are not.
- **Confidence:** High from direct data-flow inspection.
- **Resolution (2026-10-14): Fixed and verified.** After fitting each fold's XGBoost, LightGBM, and RF classifier on training rows only, `train_all_models` now adds distinct `outer_val_accuracy`, `outer_val_f1_weighted`, and applicable `outer_val_log_loss` metrics using only the untouched outer validation rows. LSTM sequence predictions are scored on outer validation sequences when supplied. Isolation Forest has no supervised target; its validation score mean/std and threshold rate are reported as descriptive diagnostics, not classification quality. A regression test verifies the training rows exclude the outer month and hand-checks accuracy/F1/log-loss on known outer predictions. Targeted ML suite: **22 passed**; full Python suite: **313 passed, 2 deprecation warnings**. No actual model training/artifact loading was performed; test uses controlled estimator fixtures.

### ML-03 — auto-retrain replaced model files without an acceptance/rollback gate (fixed)

- **Priority:** P1 (automated model promotion risk).
- **Evidence (rechecked 2026-10-14):** `services/nexus_ml/main.py::_auto_retrain_loop` builds `WalkForwardConfig(model_dir=str(symbol_model_dir(sym)))`, the same per-symbol directory used by the live ensemble; after training it pops the cached ensemble and reloads from that directory. `old_status/new_status` only report model load state; no candidate metric threshold or incumbent comparison exists. `training.py::train_all_models` calls `_save_all()` after the fold loop, and `_save_all` writes each model directly to the configured directory while catching individual save exceptions and continuing, which can leave a mixed bundle.
- **Why it matters:** A scheduled retrain can replace usable models with candidates whose verified forward performance is worse or unknown; status only checks whether artifacts loaded, not whether the candidate is better. Partial write failures can also leave a mixture of new/old artifacts.
- **Confidence:** High that the shown auto-retrain path has no performance gate or atomic promotion; runtime frequency and resulting trading impact were not measured.
- **Resolution (2026-10-14): Fixed and regression-tested.** Auto and manual retraining now write isolated per-symbol generation directories; strict save/load and feature-schema checks reject incomplete bundles. The incumbent is scored on the candidate's exact validation rows/folds, separately per supervised model/target. Promotion requires at least three folds, strictly improved mean log-loss, and no mean-accuracy regression; absent/incomparable incumbent metrics reject the entire candidate. A validated model is loaded before active-manifest replacement; the in-memory ensemble is restored on activation failure. The previous generation is retained and startup tries active then retained fallback then legacy. The unscored anomaly veto is preserved only for identical feature schema; otherwise promotion is rejected. Candidate outcomes and reason codes are recorded in the existing Redis retrain result. Tests include failed save/load, mismatched metrics/schema, rejection and promotion, activation failure, corrupt active generation, and legacy startup. See `ML_PROMOTION_20261014.md`.
- **Verification boundary:** ML tests **48 passed**, full suite **339 passed** (2 deprecation warnings), and `compileall` passed. No market-history retraining, model-artifact load from production, live Redis/DB, service startup, or MT5 action was performed. These tests establish implementation contracts, not profitability, calibration, trading readiness, or real runtime recovery.

### ML-04 — XGBoost final-fit evaluation is training data, while its early-stopping setting is unused

- **Priority:** P3 (misleading/unused training control; no stopping impact established).
- **Evidence (rechecked 2026-10-14):** Final `fit(X, y, eval_set=[(X, y)])` receives its own fit rows, but no `early_stopping_rounds` argument is passed. `_early_stopping_rounds` is set/read in the wrapper yet is not supplied to any `fit` call (`rg` shows only its declaration and assignment sites). Therefore the earlier statement that this final call performs early stopping was incorrect.
- **Impact:** The final fit may produce evaluation logs on its training data, but those logs do not control stopping in the inspected call. The parameter creates a misleading configuration surface; no effect on fit duration or model selection was demonstrated.
- **Fix direction:** Remove the unused option or implement a documented chronological early-stop policy as a separate design; do not call current behavior early stopping.

## Scope and caveats

- The ML route is mounted from `services/nexus_ml/main.py` and the service starts `_auto_retrain_loop`; these are not dead/unreferenced modules.
- This review did not validate instrument spreads/costs, broker fills, or realized PnL. The feature timestamp path was inspected from the OHLCV cache through `FeatureEvent` to Redis history; it was not verified against a live market feed.
- ML-03 code path and contract tests are fixed as described above. No real training, outer-fold evaluation on market history, or paper trading was run. ML-01/02/03 regression tests validate code contracts, not strategy profitability or model readiness.
- Do not promote/retrain models or use existing artifacts as a trading certification until candidate promotion, leakage, calibration, and historical/paper-only runtime gates are addressed.
