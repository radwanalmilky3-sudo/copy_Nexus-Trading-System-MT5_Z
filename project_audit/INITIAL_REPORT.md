## 1. الملخص التنفيذي

البنية الحالية تسع خدمات Python/FastAPI مع واجهة Next.js وRedis وDuckDB وMT5. توجد في المشروع وحدات فعلية للبيانات، الميزات، النماذج، الوكلاء، المخاطر، التنفيذ والمراقبة؛ كما توجد سجلات وتقارير سابقة لاختبارات وتشغيل وضع paper. لكن وجود الملفات والخدمات لا يثبت اكتمال تكاملها أو صحة نتائجها.

المراجعة الأولية كشفت فجوة بيانات محورية: مسار MT5 المنشور إلى Redis لا يحفظ سجل الشموع التاريخي إلى DuckDB، بينما يمكن لواجهة OHLCV أن تعيد بيانات MT5 مباشرة، ويمكن أن تعيد بيانات اصطناعية عند تفعيل الخيار. لذلك قد يبدو الرسم أو تحليل المؤشرات عاملًا دون أن يكون هناك سجل دائم صالح للتدريب أو الباك تست، أو دون أن يعرف المستهلك مصدر البيانات.

كما أن قاعدة DuckDB ذات مالك كتابة واحد منطقيًا (`nexus-data`) لتفادي قفل الملف على Windows، لكن خدمة المراقبة ما زالت تفتح عميل DuckDB للقراءة. هذا مرشح تعارض عالي الأولوية، ويجب إثبات مدى وصوله في التشغيل الحالي قبل إصلاحه. توجد تقارير اختبارات ناجحة سابقة، لكنها ليست تحققًا حديثًا لهذه الجولة؛ كما يوجد تقرير تشغيل قديم يسجل إخفاقات runtime/schema متباينة. لن نخلط تلك الأدلة بتاريخها.

## 3. المشكلات الأولية المدعومة بأدلة

### F-01 — سجل OHLCV الدائم غير موصول بمسار بث MT5

- **الأولوية المقترحة:** P1 — عالية (تدهور صامت لصحة التاريخ والتدريب)، وليست P0 لأن أثرها على البيانات الحالية/الأوامر لم يُثبت بعد.
- **الدليل:** `services/nexus_data/main.py:304-355` يجلب الشموع ويضعها في Redis لمدة 3600 ثانية وينشر آخر شمعة؛ لا يستدعي مسار إدخال DuckDB. `services/nexus_data/duckdb_store.py:221` يعرّف `insert_ohlcv`، لكن البحث عن استخدامات المشروع أظهر تعريفات فقط في هذا المسار.
- **الأثر:** إعادة تشغيل Redis أو انتهاء TTL يفقد سجل الشموع المؤقت؛ ولا يتكون تاريخ دائم من بث MT5 تلقائيًا. وقد يعتمد الرسم/المؤشرات على fallback بدل المخزن الدائم.
- **الثقة:** عالية في غياب الكتابة ضمن مسار البث كما هو مكتوب؛ يلزم إكمال call graph لكل connectors قبل الحكم على غياب كل مصادر الإدخال.
- **المعتمدون:** API السوق، مخططات الأسعار، features، backtest، التدريب وإعادة التدريب.
- **الحل المبدئي:** جعل `nexus-data` وحده يكتب شموعًا صحيحة إلى سجل دائم بمفتاح فريد `(symbol,timeframe,timestamp)` وإدخال تكراري آمن، مع إبقاء Redis للحدث/الكاش. يتطلب ذلك تصميم ترحيل اختباري على نسخة قاعدة، لا تعديل قاعدة الإنتاج مباشرة.
- **اختبار القبول:** بعد جلب MT5/fixture، إعادة تشغيل خدمة Redis أو انتظار انتهاء TTL، ثم التأكد أن التاريخ نفسه يُقرأ من DuckDB؛ واختبار إعادة الرسالة دون مضاعفة الصفوف.
- **تحديث 2026-10-14:** عولج المسار الذي كان يمنع تخزين شموع MT5 المكتملة: الناشر يحفظ الدفعة التاريخية في DuckDB عبر مالك القاعدة الوحيد، مع استبعاد الشمعة الجارية وحماية من تكرار `(symbol,timeframe,timestamp)`. تحقق باختبارات DuckDB مؤقتة (من دون فتح قاعدة المشروع الحية)؛ التفاصيل في `AUDIT_FOLLOWUP_20261012.md`. لا يحقق هذا استيراد أي نطاق تاريخي غير موجود ضمن نافذة MT5 التي تُجلب وقت التشغيل، ولا يضيف metadata للمصدر.

### F-02 — مصدر الشموع غير مميّز في استجابة API

- **الأولوية المقترحة:** P1 — عالية لسلامة العرض والبحث.
- **الدليل:** `services/nexus_data/main.py:615-645` يبحث في DuckDB ثم يعود إلى MT5 عند فراغ القاعدة، أو إلى `_synthetic_ohlcv` إذا `SYNTHETIC_FALLBACK` مفعّل. الاستجابة هي قائمة OHLCV فقط ولا تضم حقل مصدر موحدًا.
- **الأثر:** يمكن أن تتشابه البيانات الحية/الاصطناعية/المخزنة في واجهة المستهلك، فيُساء استخدامها كبيانات تاريخية أو في backtest.
- **الحل المبدئي:** عقد استجابة موحد يحوي `source`, `is_synthetic`, `as_of`, `coverage`, و`dataset_id` عند انطباقه؛ مع منع مصادر synthetic من شهادة بيانات التدريب/الباك تست. إبقاء توافق API أو إصدار نسخة جديدة واختباره.
- **الاختبارات:** كل مسار fallback يصرح بمصدره؛ مسار البحث/backtest يرفض الاصطناعي؛ UI تعرض شارة مصدر وتحذيرًا مفهومًا.

### F-03 — التحقق من OHLCV غير كافٍ لحدود البيانات

- **الأولوية المقترحة:** P2، وقد تصبح P1 عند ثبوت مرور البيانات إلى نموذج/قرار.
- **الدليل:** `shared/models.py:55-68` يتحقق فقط من `high >= low`؛ `timestamp` له قيمة افتراضية وقت الإنشاء. `tests/test_shared/test_models.py:39-41` يختبر أساسًا أن القمة أعلى من القاع.
- **الأثر:** قد تُقبل شمعة لا تشمل open/close داخل high/low، أو حجم/سعر غير محدود أو سالب، وقد يُخفى غياب timestamp تاريخي بتوليد وقت حالي.
- **الحل المبدئي:** نموذج إدخال تاريخي صارم منفصل عن نموذج live: timestamp إلزامي ومحدد المنطقة الزمنية؛ أسعار finite وموجبة (وفق نوع الأصل)، `high >= max(open,close)`, `low <= min(open,close)`, `high >= low`, وحجم finite وغير سالب، مع سياسة واضحة لمعنى tick-volume/real-volume.
- **الاختبارات:** حالات صالحة/غير صالحة وحدود NaN/Infinity والمنطقة الزمنية والتوقيت المكرر، من دون تغيير قبول رسائل live قبل مراجعة توافقها.

### F-04 — إمكانية فتح DuckDB من خدمة غير مالكة

- **الأولوية المقترحة:** P1؛ الأثر التشغيلي يعتمد على تفعيل endpoint وحالة الخدمة.
- **الدليل:** `services/nexus_monitor/main.py:311-313` ينشئ `DuckDBClient(read_only=True)`. `nexus-data` يفتح قاعدة RW باستمرار. في Windows سبق توثيق فشل فتح RO+RW متزامن في سجلات المشروع/المحادثة.
- **الأثر:** Endpoint المراقبة الذي يقرأ القاعدة قد يفشل بسبب القفل؛ وقد يختلف «health» الظاهر عن سلامة مخزن البيانات.
- **الثقة:** مرتفعة على وجود مسار الفتح، ومتوسطة على وقوعه دوريًا قبل فحص استدعاءات endpoint وإعادة إنتاجه في بيئة معزولة.
- **الحل المبدئي:** تمرير القراءة عبر واجهة داخلية مصادق عليها وallowlisted في `nexus-data` أو Redis metrics مناسبة، وعدم فتح الملف من monitor/API. لا نقبل SQL من العميل ولا نفتح القاعدة live لأجل إثبات المشكلة.
- **تحديث 2026-10-14:** أصلح endpoint `nexus-monitor` الأداء ليقرأ سجل الصفقات من واجهة `nexus-data` بدل فتح DuckDB read-only من عملية ثانية؛ اختبار بعقد HTTP وهمي يغطي النجاح وفشل المصدر. المسار لم يُعثر عليه مستهلكًا من لوحة التحكم أو API gateway، لكنه يبقى endpoint صالحًا للاستدعاء المباشر. هذا لا يثبت أن كل قارئ DuckDB في المستودع أزيل؛ بقي فحص الاعتماديات القديمة والمستهلكين الآخرين.

### F-05 — باك تست الشموع وتدقيق البيانات ليسا واضحين كوظائف واجهة

- **الأولوية المقترحة:** P2 (فجوة منتج/تكامل، لا عطل مؤكد في خدمة).
- **الدليل:** API السوق `services/nexus_api/routers/market.py:39+` يمرر `count` فقط رغم أن خدمة البيانات تقبل `start/end`. لم يُعثر على route استيراد تاريخي في جرد صفحات Dashboard السابق. README المحلي يصف Backtest على الصفقات المغلقة (يجب التحقق من توافق ذلك مع محرك backtest الموجود).
- **الأثر:** لا توجد تجربة واضحة للمستخدم لاستيراد/معاينة/اعتماد مجموعة بيانات؛ كما أن نطاق التاريخ لا يعبر بوابة السوق في طلب candles.
- **الحل المبدئي:** شاشة مركز بيانات موصوفة بالتفصيل أدناه، وتمرير نطاق التاريخ بعد تثبيت contract ومصدر القراءة.

## 4. مخاطر/ادعاءات لم تُحسم بعد

هذه ليست نتائج مثبتة حتى يُقرأ المسار كاملًا ويُختبر:

1. هل auto-retrain يختار نموذجًا جديدًا دون بوابة مقارنة/ترقية؟ توجد جدولة وتدريب؛ نحتاج مراجعة الجزء الذي ينشر النماذج، و`ensemble.py`، وسجل feature history واختبار walk-forward والتقسيم الزمني.
2. هل نماذج الميزات تتسرب إليها معلومات مستقبلية؟ لا يوجد استنتاج من وجود `walk-forward` وحده؛ يجب تتبع timestamps، labels، joins والتطبيع داخل كل fold، وفحص notebook/model fixtures.
3. `nexus-monitor` كان يفتح DuckDB مباشرة في endpoint الأداء؛ المسار عُدّل إلى proxy عبر `nexus-data` واختبر. تحقق لاحقًا من عدم بقاء قارئ مباشر آخر أو consumer غير موثق.
4. هل الخدمات الواردة في المخطط كلها مستقلة فعلًا؟ يجب رسم import/API/Redis graph من entrypoints الحالية لا README فقط.
5. سلامة الأسرار والاعتماديات وواجهات داخلية: لم يُجرَ فحص CVE أو secret scan في هذه المرحلة؛ لا يُسمح بطباعة `.env` أو استخدام فاحص مجهول.
6. مشكلات persistence في fundamental وغياب timeout في عميل Redis للأخبار مذكورة في `TEST_RESULTS.md` بتاريخ 2026-10-10؛ يلزم إعادة فحص الكود الحالي واختبارات فشل Redis/قاعدة البيانات قبل اعتبارها مفتوحة.
7. هناك `V6_1_FINAL_VERIFY_REPORT.txt` بنتيجة تاريخية مختلطة: اختبارات عامة ناجحة، لكن endpoints وschema/runtime evidence كثيرة فشلت بسبب احتمال خدمة قديمة؛ يجب مطابقة النسخة الجارية الحالية قبل أي استنتاج.

### خط الأساس الأصلي (وفق README المنشور)

المستودع الأصلي يصف 9 خدمات، مسارًا event-driven عبر Redis Streams، و`run.py` كمشرف يعيد تشغيل الخدمات. دورة القرار المعلنة هي: MT5 → `nexus-data` → `nexus-features` → `nexus-ml` → `nexus-agents` → `nexus-risk` → `nexus-executor` → MT5. ويذكر README أن DuckDB تُستخدم لـtrade memory، بينما Redis يحمل streams/cache. كما يقرر أن veto المخاطر غير قابل للتجاوز، ويعرض backtest على الصفقات التاريخية المغلقة. هذه أوصاف التصميم الأصلي وليست إثباتًا أن كل ميزة مطبقة أو مجرّبة.

### مقارنة حدودها وأثرها

لا يمكن حتى الآن نسبة أي فرق إلى «تطوير محلي» مقابل GitHub على مستوى ملف/commit؛ الجدول يقارن ادعاءات README بالأدلة الجزئية من الشجرة المحلية التي فُحصت سابقًا. التدفق النظري: MT5 → `nexus-data` → Redis Streams → `nexus-features` → `nexus-ml` → `nexus-agents` → `nexus-risk` → `nexus-executor` → MT5؛ والـDashboard عبر API Gateway. التنفيذ يضيف حقيقة مهمة غير ظاهرة في الرسم: DuckDB للتاريخ الدائم، وملفها مقفول عمليًا بعملية واحدة على Windows. لذلك التوصيف الصحيح يجب أن يميز بين:

- **مسار لحظي:** Redis Streams للرسائل؛ Redis Cache للحالة/آخر الشموع.
- **مسار تاريخي:** DuckDB تملكها `nexus-data` فقط وتُقرأ عبر واجهات داخلية محددة.
- **مسار تقديم الواجهة:** Browser → `nexus-api` → خدماتها/بياناتها؛ لا اتصال مباشر من المتصفح إلى DuckDB أو MT5.
- **مسار التدريب/الباك تست:** dataset محدد الإصدار ومثبت المصدر/الفترة/المنطقة الزمنية/قواعد التحويل، لا cache قابل للانتهاء.

التعديلات على event contracts قد تمس features وML وagents؛ تغييرات schema تمس data API وmonitor وAPI وdashboard؛ وتغييرات نافذة القرار/السعر قد تمس risk/executor. لذلك لا ينبغي إصلاح كل شيء في commit واحد أو ترحيل قاعدة حية دون backup وخطة استرجاع.

## 6. التطوير المقترح — مرتّبًا حسب المخاطر

### أ. أساس البيانات (قبل بناء شاشة الاستيراد)

1. رسم ملفّي دقيق لكل connector: المصدر → تطبيع الرمز/الإطار/الوقت → validation → Redis → persistent store → consumers.
2. اعتماد مصدر وحيد لكتابة DuckDB وإزالة قارئي الملف المباشرين من الخدمات، بعد حصر جميع الاستعمالات.
3. تصميم migration additive/نسخ احتياطي: مفتاح تكرار منطقي، metadata المصدر و`import_run_id`, وقت الاستلام، وربما volume-kind؛ dedupe audit قبل constraint.

### ب. شاشة «مركز البيانات التاريخية»

**التنقل:** عنصر رئيسي في Dashboard باسم «البيانات التاريخية» تحت مجموعة البيانات/الأدوات؛ لا تدمجها مع سجل الصفقات. تتكون من 4 صفحات أو تبويبات ذات روابط ثابتة.

#### 1) نظرة عامة — `/dashboard/data`

- مؤشرات أعلى الصفحة: حالة الاتصال بالمصدر، آخر تحديث، عدد الرموز والإطارات المغطاة، حجم السجل، آخر استيراد وحالته.
- جدول تغطية: الأصل، اسم الوسيط، فئة الأصل، timeframe، أول/آخر شمعة UTC، عدد الشموع، نسبة التغطية المتوقعة، التكرارات، الفجوات، المصدر، شهادة الجودة.
- فلاتر: الأصل، الفئة، timeframe، المصدر، الحالة، الفترة.
- تنبيهات صريحة: «بيانات حية وليست محفوظة»، «مصدر اصطناعي»، «تأخر التحديث»، «سجل تاريخ غير كافٍ للتدريب»، «شهادة منتهية بعد تغيّر dataset».
- إجراءات: استيراد، فتح مجموعة البيانات، تنزيل تقرير الجودة؛ لا إجراء حذف جماعي افتراضيًا.

#### 2) معالج الاستيراد — `/dashboard/data/import`

**الخطوة 1: المصدر**

- `source_type`: ملف CSV في MVP، ثم MT5 التاريخي بعد دعم date range.
- ملف: اختيار/سحب، حد حجم معلن، امتداد مسموح، مع بصمة SHA-256 من الخادم لا من المتصفح فقط.
- إن كان MT5: الحساب/الوسيط المقروء (دون كلمة مرور)، symbol broker name/alias، الاتصال وحالة terminal.

**الخطوة 2: تعريف البيانات**

- `symbol` (من سجل الأصول مع alias وسيط ظاهر)، `timeframe` من M1/M5/M15/M30/H1/H4/D1.
- `timestamp_column`, `timestamp_format`, `timezone` (UTC افتراضيًا، والرفض/التحذير للوقت المحلي الملتبس).
- `open`, `high`, `low`, `close`, `volume` + نوع الحجم (tick/real/غير معروف).
- تاريخ بداية/نهاية متوقعة، delimiters/decimal separator، ترميز CSV، وتطبيع أسماء الأعمدة.

**الخطوة 3: معاينة والتحقق — لا كتابة في هذه الخطوة**

- أول/آخر صفوف، نطاق UTC، صفوف خام/صالحة/مرفوضة، أعمدة مطابقة، أنواع البيانات.
- تحقق OHLC، NaN/Infinity، الأسعار السالبة/الصفرية حسب asset class، timestamps مفقودة أو مكررة أو مستقبلية.
- تكرار داخلي، overlap مع الموجود، out-of-order، فجوات مقارنة بجلسة السوق (weekends/holidays ليست تلقائيًا فسادًا).
- تأثير الاختيار: `duplicate_policy` الافتراضي `skip`; خيار `replace/update` يتطلب صلاحية وتأكيدًا ويعرض عدد الصفوف المتأثرة قبل التنفيذ.
- نافذة مقارنة: عدد جديد/موجود/سيتم تجاهله/سيحدث، ومصدر وسياق كل صف.

**الخطوة 4: تنفيذ الاستيراد**

- زر واضح «اعتماد الاستيراد» بعد نجاح التحقق، اسم اختياري للمجموعة، `purpose`: chart / backtest / training.
- `dry_run` افتراضي قبل الاعتماد؛ معرف job، تقدم، إجمالي/مقبول/مرفوض/متجاوز، وقت البدء والانتهاء، زر إلغاء آمن.
- السلوك عند الفشل: لا commit جزئي غير معلوم؛ إما transaction آمن لمجموعة قابلة للإدارة أو chunks موثقة باستئناف idempotent. عرض سبب الفشل ومرجع السجل دون SQL داخلي.

#### 3) سجل الاستيرادات — `/dashboard/data/imports`

أعمدة: `import_id`, المصدر، الملف/الوسيط، الرمز، الإطار، النطاق، الحالة، عدد الصفوف، الأخطاء/التحذيرات، SHA-256، المنشئ، بدأ/انتهى، نسخة importer/schema، `dataset_id` ونتيجة الجودة. فلاتر وتفاصيل قابلة للتنزيل. إعادة التشغيل تنشئ run جديدًا مرجعه الأصل، ولا تعدل run سابقًا.

- بطاقة الحالة: صالح للغرض / صالح بتحذيرات / مرفوض، الغرض، المصدر، الفترة، وقت الإنشاء ونسخة قاعدة القواعد.
- ملخص الحجم والتغطية حسب جلسات السوق، gaps/duplicates/outliers/invalid، changelog للمعالجة.

- اختبارات الصلاحية مع pass/warn/fail وعتبة كل فحص وسبب القرار.
- قائمة نتائج قابلة للتصفية والتنزيل، لا تُظهر الأسرار ولا ترفع بيانات مجهولة.
- إجراءات: اعتماد للاستخدام المحدد، إبطال شهادة بعد تعديل البيانات، مقارنة إصدارين، تصدير تقرير.

### ج. شاشات مساندة لهذا التدقيق

1. **صحة الخدمات والتبعيات:** READY/DEGRADED/UNHEALTHY بفرق واضح، آخر heartbeat، Redis/DB/MT5/LLM، آخر نجاح وفشل؛ لا تكتفِ بـ READY من دون dependency probes.
2. **تتبع قرار الإشارة:** event/correlation ID يربط شمعة مصدرها معروف → feature version → model version/votes → agent verdict → risk decision → executor result. عرض سبب الرفض أو عدم التنفيذ.
3. **إدارة النماذج والتدريب:** model registry، بيانات التدريب وشهادتها، فترة train/validation/test، fold metrics، baseline/current، leakage checks، artifact hash، تاريخ الترقية/التراجع. لا ترقية تلقائية دون gate.
4. **لوحة مخاطر وتنفيذ:** تعرض وضع الورقي/الحي مصدره runtime config، auto-trade state، أسباب veto، order idempotency، broker ack/slippage/spread، kill-switch. أي خلل dependency يبين أن التنفيذ محظور.
5. **قائمة الإشارات/التنبيهات:** مستويات حرجة، نص يحدد أثر المستخدم، توقيت UTC ومحلي، آخر تحديث، رابط إلى سجل مفصل وإجراء آمن. لا تخفي alerts المتكررة أو تعطي OK رغم degraded.
