# Architecture Insights — fx-trading-system (Reference Audit)

Agent: A6 (Architecture). Scope: principles extracted from `src/fx_system/engine.py`, `planner.py`, `config.py` (with structural context from the package and CLI). Read-only analysis; no code copied.

## Engine Loop and Execution Pipeline Design

The backtest engine is built around a single, deterministic, event-driven loop over a merged timeline of timestamps unioned across all symbols' data indexes. Rather than iterating per symbol (which would scramble cross-asset ordering), one global clock drives every decision, guaranteeing reproducibility and a well-defined precedence of events. Each bar tick executes a fixed, documented phase ordering: time-based exits first (at bar open, before the bar's range is "observed"), then existing stop/target intrabar checks, then new signal entries, then session policies (weekend close), then equity snapshot and risk kill-switch evaluation. This phasing is an explicit anti-look-ahead-bias contract: signals timestamped on a bar are scheduled to the *next* bar's open via index search, intrabar exits resolve stop-vs-target conflicts conservatively (stop wins when both are touched), and entries filled at a bar's open are immediately re-exposed to that same bar's range. Costs are not an afterthought bolted onto fills; they are a separately injected execution-cost model (spread, slippage, commission, and calendar-aware swap including triple-rollover Wednesday) consulted at every entry, exit, and even at mark-to-market liquidation valuation, with a stress multiplier that widens observed spreads when computing equity. Rejected signals and rejections of whole groups are recorded with reasons, producing a full audit trail rather than silently dropping decisions.

A second structural pillar is atomic group execution. Signals may carry a group identifier (basket/hedge legs); the engine groups same-timestamp candidates, attempts each leg through the risk manager, and if any leg of a multi-leg group fails, rolls back every position opened by that group and logs an atomic-group rollback rejection. One-symbol positions can fail individually; multi-leg strategies cannot be half-executed. Risk management is factored into a dedicated portfolio risk manager consulted at entry time with live equity, drawdown, daily-loss, exposure, and correlation state, plus a global irreversible halt flag once max drawdown is breached — the system fails closed, never re-opens, and every subsequent signal is rejected with a distinct reason code. The engine's own configuration surface is deliberately narrow (risk config, cost config, account currency), and everything else arrives as inputs: data mappings, pre-computed signals, metadata. This makes the engine a pure simulation kernel: same inputs, same outputs, no hidden clock, no I/O, no randomness.

## Planner: Research Planning and Experiment Orchestration

The planner embodies a "plan-then-act" separation: producing order intentions is a pure, no-side-effect operation distinct from any submission path. It consumes the latest *closed* bars only, regenerates ensemble signals from the approved strategy set, and emits frozen, immutable order proposals that carry a deterministic content-derived identifier (hash of timestamp, symbol, side, strategy, and group), a reference price, stop, target, holding cap, and an expiry timestamp of roughly two bar intervals. Deterministic IDs make plans idempotent and reconcilable — the same market state plus config yields the same plan identity, enabling downstream deduplication and audit. Expiry is a staleness guard: a plan is only valid for the immediate decision window, after which market conditions must be re-evaluated. Critically, the planner reuses the *same* risk manager and the same atomic-group rollback semantics as the backtest engine, so paper planning and historical simulation cannot drift apart in risk or group behavior; plan-time and execute-time share one risk truth. Approval gating is expressed in configuration (enabled vs. paper-enabled strategy flags), and an explicit opt-in flag is required to even consider unapproved strategies in planning.

Experiment orchestration across the wider system follows a staged pipeline philosophy visible in the CLI and runners: data acquisition, intake ledgers, deep audits, coverage manifests, feature/factor building, screening, freeze, forward evaluation — each stage a separate command with its own config preset and output artifact. Long-running research is decomposed into runner modules (intraday, long-horizon, portfolio runners) that share the config/model substrate but own their orchestration loops. Research discipline is architectural, not procedural: the pipeline physically separates "inputs built" commands from "fitting/selection" commands, and command help text declares that certain stages generate research inputs only and grant no trading approval. The freeze stage takes an explicit date range (end exclusive is mandatory), a declaration file, and a registry — turning a research cutoff into a versioned, auditable artifact rather than a parameter someone can quietly retune after seeing results.

## Configuration Management: Typed Config, Validation, Presets

Configuration is a typed, schema-enforced contract built with a structured validation framework: a composed root model nests domain sections (data, costs, risk, strategies, ensemble, output), each a model with field-level numeric bounds (greater-than/less-than-or-equal constraints on risk-per-trade, drawdown limits, leverage, correlation thresholds, retry counts) so that physically nonsensical values are rejected at load time, not discovered mid-run. Closed vocabularies are encoded as literal types — data provider, bar interval, price mode, and the finite set of strategy names — eliminating typos and unbounded free-text strategies. Cross-field invariants live in a root model validator: at least one strategy must be enabled, enabled names must be unique, and paper-enabled implies enabled. Symbol lists are normalized through a domain parser and checked for duplicates during validation. The result is that an invalid configuration cannot exist in memory; the failure surface is a single, early, descriptive validation error. A dedicated `validate-config` CLI command makes this check a first-class gate before any run.

Presets are first-class, version-controlled research artifacts rather than ad-hoc flags. The `configs/` directory holds named YAML files for distinct purposes: default demo runs, intraday research, long-horizon candidate screens, a WP6 freeze configuration, research-fixed cost fixtures versus broker-cost acquisition plans, and intake universes. Each run is therefore fully described by (commit, config preset, data snapshot), which is the reproducibility backbone. Cost assumptions deserve special note: research-only synthetic costs are modeled explicitly as fixtures with distinct multipliers and directories, structurally separated from anything resembling broker-real costs — the configuration schema itself prevents conflating fixture costs with formal ones. Paths, output directories, and seeds live in config (the data section carries an explicit integer seed for synthetic generation), never hardcoded. This "config-as-experiment-record" pattern means every produced artifact can be traced back to the exact typed configuration that generated it.

## Module Boundaries, Domain Models, and State

Despite a flat package layout, module boundaries follow a clean single-responsibility and directional-dependency discipline. The engine (simulation kernel) depends only on config, domain models, the FX rate graph, and the risk manager — never on research, data ingestion, or the CLI. Signal generation (research, ensemble, factors, indicators) is upstream: signals are produced elsewhere and enter the engine as immutable value objects. Data acquisition and normalization (CSV/Yahoo/synthetic/broker/Dukascopy adapters, intake ledgers, daily caches) are isolated behind a data-config provider selector. Cross-currency conversion is centralized in a single rate-graph service used by both engine and planner, preventing scattered, inconsistent FX math. Orchestration shells (CLI commands and dedicated runner modules) sit at the edge, composing library functions; domain and kernel layers never import them. External side effects (broker submission) are quarantined in their own module with explicit confirmation gating, physically separated from planning.

Domain state is modeled with immutable, frozen records: signals, positions, trades, equity points, and proposals are value objects; mutation happens only through well-defined transitions inside the engine loop. The position lifecycle is an implicit state machine whose transitions are exhaustively labeled by exit-reason codes — time-based max-hold, stop, target, opposite-signal flip, weekend policy, drawdown kill, end-of-data — giving every trade a causal explanation and enabling downstream analytics to aggregate by cause. The global run state adds a one-way halted transition (drawdown kill), after which entry is permanently refused for the remainder of the run. Higher-level data contracts use explicit state fields on disk (intake verdict, formal-ready flags) with a stated single-source-of-truth rule: when documents and disk disagree, disk wins and the discrepancy is flagged. Fail-critical governance flags (trading approval, formal-net-ready, label-opening) are declared non-flippable by automated agents — safety state is protected by process and policy, not merely by code comments.

## Reproducibility and CLI Composition

Reproducibility is engineered at multiple layers. Determinism: the engine's global-timestamp loop, confidence-ordered signal scheduling, and group ordering make runs a pure function of inputs; the planner's content-hash IDs make plans reconcilable; synthetic data generation carries an explicit seed in config. Artifact versioning: research configs, declarations, and registries are version-controlled YAML; large market data and outputs stay out of git but are pinned by versioned directory names, intake ledgers, and SHA sidecar manifests that enable exact re-acquisition; audit closures produce JSON artifacts recording per-universe pass/fail with hashes. Point-in-time correctness is a first-class module concern — vintages, publication calendars, and available-time checks ensure external data cannot leak into decisions made before its release. A research registry records disclosed assumptions, factors, and test counts, so the cumulative multiple-testing surface is tracked rather than forgotten.

The CLI is a thin composition root built on a typed command framework with a no-arguments-shows-help posture. Commands are one-purpose verbs in a pipeline — download, intake-ledger, audit, build, screen, freeze, forward-evaluate, paper-plan, submit — each with typed options, default output paths under a dedicated outputs tree, and early mutual-exclusion validation (for example, refusing both a canonical swap CSV and a legacy swap directory). Safety is expressed as explicit confirmation switches: the broker submission command refuses to act without an explicit practice-confirmation flag, and freeze commands require exclusive end dates. Every command maps directly to a library function with the real logic living in importable modules, so the same operations are testable without the CLI. This composition style — small composable commands, typed config in, artifacts out, side effects gated behind explicit intent — is what allows an ambitious multi-stage research pipeline to remain auditable end to end.

## Key Principles for Nexus

For our project (9 FastAPI microservices + Redis + DuckDB + Next.js dashboard, orchestrated by `run.py`), the transferable principles are:

- **Deterministic event loops with explicit phase ordering.** In any trading/decision path (signal generation, order lifecycle, risk checks), define a fixed per-tick phase order (risk check → entry → exit → mark-to-market → kill-switch) and schedule signals to the next actionable timestamp — never evaluate a decision against data it could not have seen. Document stop-vs-target and conflict precedence explicitly.
- **Fail-closed global kill switches with reason codes.** Every rejection (risk deny, stale signal, halted system, expired proposal) must be persisted with a machine-readable reason, and a breached drawdown/loss limit must set an irreversible halt for the session. No silent drops anywhere in the pipeline.
- **One typed, validated config contract per service — with cross-field invariants.** Use schema validation with numeric bounds, closed enums, and cross-field rules (e.g., "paper mode requires enabled", "at least one strategy enabled") loaded once at startup. Expose a `validate-config`-style preflight in `run.py` before any service boots; make invalid states unconstructable.
- **Config-as-experiment-record with versioned presets.** Every run of the ensemble/backtest/ML services should be identified by (git commit, config preset, data snapshot). Keep environment-specific values (ports, Redis URLs, DuckDB paths) and strategy/risk parameters in versioned, per-scenario config files, not scattered constants.
- **Plan/act separation with deterministic, expiring order proposals.** Trading actions should originate from immutable, content-hash-identified proposals with built-in expiry, produced by a pure planner that shares the exact same risk engine as execution. Broker/MT5 submission must be a separate, explicitly confirmed step — the dashboard must never mutate orders directly.
- **Atomic multi-leg actions with rollback.** Any basket, hedge, or multi-service operation (e.g., open position + notify + persist) must be all-or-nothing with logged rollback on partial failure; single-leg failures degrade individually, never leave half-applied portfolio state.
- **Immutable audit artifacts and disk-as-SSOT.** Persist trades, equity points, rejections, health checks, and intake verdicts as append-only records with hashes and timestamps; when docs, caches, or DB copies disagree with the authoritative store, the store wins and the conflict is flagged, not averaged away.
- **Thin orchestration, deep library.** Keep `run.py` and each FastAPI service's entrypoint as composition roots that wire typed config → library services → routers; keep business logic in importable, unit-testable modules with strict dependency direction (API → services → domain), and quarantine MT5/external side effects behind explicit confirmation gates.
