# DATA COMPARISON — Reference (`fx_system`) vs Nexus (`services/nexus_data`)

**Agent:** A7 (Data Comparator) — read-only survey.
**Reference:** `fx-trading-system-main/src/fx_system/` (`data.py`, `dukascopy_intake.py`, `dukascopy_daily_cache.py`, `point_in_time.py`, plus `macro_vintages.py` skim and `tests/test_dukascopy_intake.py`).
**Ours:** `services/nexus_data/` (`main.py`, `duckdb_store.py`, `mt5_connector.py`, `redis_cache.py`, `quality/*`, `imports/*`, `data_quality_contracts.py`, `fundamental_schema.sql`).

## Ingestion model

The reference system is a **batch, file-oriented research intake**. Everything flows through one provider abstraction (`data.py` / `load_from_config`) with five interchangeable sources: a CSV directory, Yahoo, a synthetic generator, OANDA practice candles, and a Dukascopy tick downloader. The Dukascopy path is the deepest: it decomposes a date range into individual UTC hours, downloads LZMA-compressed tick files on a bounded thread pool, retries with exponential backoff, and aggregates hour ticks into 1h/4h/1d bars only when a minimum number of source hours is present. Every hour is structurally validated at decode time — record-size multiples, monotonic millisecond offsets, crossed or non-positive quotes, non-finite or negative volumes, and a per-symbol price divisor that must be explicitly declared or the parse fails. Coverage is not assumed: each result carries counters for requested, available, no-data, failed, cached and downloaded hours plus a computed hour-coverage ratio, and the still-forming final candle is dropped against a supplied "now" rather than the wall clock at read time.

Ours is a **live, long-running service ingestion** rather than a batch replay. `main.py` owns three concurrent loops: tick streaming from the MT5 connector into Redis cache + DuckDB + a Redis Stream fan-out; an OHLCV publisher that polls the terminal every 30 seconds for a fixed window of bars (default 300, configurable timeframes) and persists only closed candles; and a gap-detection backfill task that plans missing intervals inside a conservative 7-day lookback (bounded to 4 intervals and 500 bars per cycle, minimum 600 s between cycles), records provider-answered windows so weekend/holiday holes are never re-requested, and labels rows by source (`mt5_poll`, `mt5_backfill`, `mt5_range`). The forming-bar invariant (`is_closed_bar`, `duckdb_store.py:47`) is enforced at every write, provider errors are retried and eventually trigger a reconnect, and range queries transparently pull history from MT5 and persist it. This is operationally appropriate for a trading stack — but it is a fundamentally different shape: no raw payload is archived, there is no hour-by-hour decode audit, and the historical depth available to any backtest is whatever happens to be in DuckDB at the moment.

## Storage

The reference keeps truth in **immutable, hash-anchored artifacts**. Bar CSVs are written with a `_data_manifest.json` carrying a schema version and a per-symbol SHA-256 that is re-verified on every load (a mismatch raises, it does not warn), along with row counts, start/end timestamps, dropped-invalid-OHLC counts, price mode, mean spread, swap availability and per-row source metadata. The 10-year tick universe lives in per-symbol SQLite files received under a formal intake contract: each database must have both a `.sha256` sidecar and a `.json` sidecar that must agree with each other, must declare the parser/schema/provider/base-URL metadata, and must match a batch `_sqlite_manifest.json`; only then can a symbol reach `formal_ready`, and a partial or mismatched symbol is recorded as `present_incomplete`/`legacy_range_mismatch`/`transfer_failed` rather than silently dropped from the universe. A second layer, `dukascopy_daily_cache.py`, stores derived daily bars plus session and transfer audits, and is loadable only when its own whole-file hash is intact **and** every source database still matches its transfer receipt.

Ours stores everything in a **single DuckDB file with a single serialized writer** (`nexus.duckdb`, one connection behind an asyncio lock), plus Redis for the hot path. That buys excellent query speed and simple operations, but the durability and integrity story is much thinner: `ticks` are pruned after 7 days and `ohlcv` after 365 days, so the store is a rolling window rather than an archive; there are no content hashes, no manifests, and no receipts for anything. Provenance is limited to three columns on `ohlcv` — `source`, `quality`, `fetched_at` — with a migration that back-fills old rows to `source='mt5'`, `quality='ok'`. Deduplication is `WHERE NOT EXISTS` on (symbol, timeframe, timestamp), i.e. **first write wins**: if MT5 ever corrects a completed bar, the correction is silently discarded and there is no revision/version column to detect the discrepancy. The upside is real — a provenance endpoint exposes per-bar source/quality, coverage stats and recent backfill runs, and the fundamental store does define `known_at`/`published_at`/`data_vintages`/`macro_releases` tables — but for market data there is no equivalent of the reference's hash chain.

## Point-in-time / vintage handling (look-ahead risk)

This is the largest divergence. The reference treats "what was knowable when" as a first-class contract. `point_in_time.py` requires every rate/forward/positioning row to carry both `observation_time` and `available_time`, rejects rows where observation is later than availability, forbids duplicate entity/availability pairs, enforces per-row source/provenance/quote-quality enumerations, verifies a sidecar manifest whose declared source catalog must cover every observed triple, and then joins to feature timestamps with a **backward as-of merge under an explicit staleness tolerance** (45 days for rates, 14 days for positioning). Promotion to "verified historical market contract" is a computed gate, and a `fingerprint()` method hashes the PIT dataset — optionally truncated at an `available_through` timestamp — so an experiment can be bound to exactly the data state that existed at decision time. `attach_historical_swaps` follows the same rule explicitly documented as "future rows are never backfilled", and `macro_vintages.py` computes growth rates only from two levels inside the *same* release vintage, never splicing later-revised history into an earlier decision. CFTC positioning additionally demands `verified_actual_publication` availability and `verified_as_published_vintage` values, on the explicit grounds that a current revised historical archive is not point-in-time data.

**Ours has no equivalent for market data, and only a partial one elsewhere.** A bar in DuckDB has its event timestamp and an ingestion timestamp, but nothing binds a query or a backtest to "the data as it stood at time T": there is no availability cut-off, no dataset fingerprint, no revision history (first write wins), and no staleness policy. The fundamental schema does contain `known_at`, `source_published_at`, `data_vintages` and `macro_releases` columns/tables, and `quality/report.py` defines a `ResearchContext` carrying `available_at`, `vintage_id` and a `pit` flag — but that vocabulary is declarative only: the quality/report modules have **no call sites outside their own package**, so nothing in the ingestion or query path enforces an as-of join, a staleness bound, or a manifest hash. The practical consequence is look-ahead risk by construction: any feature computed today over DuckDB history sees bars that were fetched after the decision point being simulated, corrected bars are indistinguishable from original ones, and no reproducible receipt exists to prove otherwise. A second, smaller leak: synthetic fallback generators (`_synthetic_tick`, `_synthetic_ohlcv`) can be returned through public endpoints when `NEXUS_DATA_SYNTHETIC_FALLBACK=1`, and the response body carries no marker distinguishing synthetic from real rows — only log lines and the `/health` `data_mode` field.

## Data quality audits

The reference validates at three levels. On ingest, `validate_bars` enforces OHLC invariants (low ≤ open/close ≤ high, high ≥ low, strictly positive prices), complete bid/ask column sets, bid ≤ ask and mid-inside-quote crossing checks, duplicate-timestamp rejection, UTC normalization, numeric coercion, and a raise-or-drop policy whose drop count is written into the manifest — so data loss is always counted, never silent. The intake layer adds a state machine over range/sidecar/manifest/transfer conditions with an explicit overall verdict. The daily layer adds a full **session audit**: expected vs decoded vs no-data vs missing hours, the concrete missing-hour list, payload-hash verification counts, duplicate-timestamps-removed, quote age at session open/close/boundary, and a suppression reason whenever a bar is withheld. A separate tick-level G0 audit script sweeps every database for zero error/crossed/SHA-mismatch/LZMA/timestamp-regression/missing-hour findings, and its JSON closure report is treated as evidence.

Ours has a well-designed but **disconnected** quality layer. `quality/validators.py` implements duplicate keys, monotonic ordering, gap detection against the expected interval, and outlier thresholds with quarantine records; `quality/report.py` projects findings into research contracts; `imports/contracts.py` defines canonical record types; and `data_quality_contracts.py` declares dataset/import/quality-run/quarantine/lineage/artifact contracts (its own docstring states it is declarative-only). None of these are reachable from `main.py` or `duckdb_store.py`, and no test under `tests/` references them — so on the live path every row is written with the default `quality='ok'` regardless of its actual content, ticks are never checked for crossed quotes or non-positive prices, and OHLCV invariants are never re-checked after the provider returns them. What does exist is good: forming-bar rejection with counters, dedupe, gap planning with backfill-run records, timezone-aware range validation before any provider call, provider-error-vs-empty-range disambiguation (so outages are not recorded as market closures), and a provenance endpoint exposing coverage. But there is no persisted audit artifact equivalent to the session audit, and no pass/fail gate that can block or quarantine a bad batch.

## Caching

The reference caches at the **raw layer**, keyed by parser version: downloaded tick files land in the cache only after they parse, corrupt cached entries are renamed out of the way and re-fetched, confirmed-empty hours get `.missing` markers so a multi-year download can resume without re-probing, and the whole cache is namespaced under `dukascopy-bi5-v1` so a parser change cannot silently reuse incompatible bytes. The derived daily cache adds a second tier that is itself hash-anchored and receipt-checked at load time. Ours caches at the **serving layer**: Redis holds recent tick history, a JSON snapshot of the latest bars under a 1-hour TTL as the feature-engine input, and backfill-window records that prevent repeatedly re-requesting answered ranges. Both designs are internally coherent for their purpose (reproducible research vs low-latency serving), but ours provides no tamper evidence, no raw-payload resume, and no invalidation on schema/parser change — a consumer of the Redis OHLCV key cannot tell whether the JSON it reads was produced by today's code or yesterday's.

## Contract testing

The reference pins its data contract in tests: `tests/test_dukascopy_intake.py` asserts the frozen 14-symbol universe and its slow/fix-W splits, that the unified range contract rejects a legacy end date, that an on-disk config must match the in-code frozen contract, that a reordered universe is rejected, and that the ledger produces the correct state machine verdicts for missing and legacy symbols. Complementary contract modules exist for cost and forward-point collection, and the intake ledger itself is written to disk as a machine-readable verdict. Ours tests behaviour rather than contracts: forming-bar rejection, duplicate-batch idempotency, provider error not masked as missing data, inverted date ranges rejected before hitting the store, timeframe validation before provider calls, WAL recovery, sensitive-read and subscribe authorization, and the trade-close consumer. These are meaningful and pass, but nothing pins a dataset range, symbol universe, schema version, provenance completeness, or quality-run gate; the four contract/quality modules that would carry such a contract are untested because they are unused.

## Actionable Recommendations

Ranked by impact on correctness/research integrity first, operations second.

1. **Bind every query and backtest to an as-of cut-off (High).** Add an availability dimension to market data (at minimum `fetched_at`-based as-of filtering with an explicit staleness/availability policy) and a dataset fingerprint API that hashes a series restricted to rows available at a supplied decision time. Without this, any historical evaluation carries unquantifiable look-ahead risk and cannot be reproduced.
2. **Wire the existing quality layer into the write path (High).** `quality/validators.py`, `quality/report.py`, `imports/*` and `data_quality_contracts.py` are already written; make ingestion emit real `QualityRun`/`Quarantine` records and stop defaulting `quality='ok'`. A batch that fails duplicate/ordering/outlier/OHLC-invariant checks should be quarantined, not persisted and labelled clean.
3. **Add integrity manifests and stop trusting first-write-wins (High).** Persist per-(symbol, timeframe) coverage manifests with content hashes and row counts, and add a revision-aware write policy: if a completed bar differs from the stored one, record a revision instead of silently discarding the correction. This is the DuckDB analogue of the reference's SHA/sidecar/receipt chain.
4. **Make synthetic data unambiguous in-band (Med).** Any row served from synthetic fallback must carry a machine-readable flag in the response (and ideally a distinct `source` value in storage), so no downstream consumer can train or trade on fixture data without seeing it. Keep the current fail-closed default.
5. **Publish a persisted coverage/session audit (Med).** Extend the provenance endpoint's coverage stats into a durable audit artifact per (symbol, timeframe, day): expected vs present bars, provider-answered empty windows, backfill attempts, and missing intervals — the equivalent of the reference session audit, so gaps are accountable facts rather than log lines.
6. **Introduce a frozen data-contract test suite (Med).** Pin symbol universe, supported timeframes, retention limits, provenance column presence, schema/migration versions, and quality-gate behaviour in tests that fail on drift — mirroring the reference's frozen-universe/range/config contract tests.
7. **Reconsider retention for anything used as research evidence (Med).** A 365-day OHLCV window plus a 7-day tick window cannot support re-evaluation or audit after the fact; either raise retention for symbols/timeframes under study or export immutable periodic snapshots with hashes before pruning.
8. **Record a formal intake verdict for restored/backfilled history (Low).** When OHLCV history is imported from outside the live poll (range pulls, restores, any offline file import), run it through the same contract checks and emit a machine-readable readiness verdict rather than inserting directly.
