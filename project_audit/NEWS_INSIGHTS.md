# A2 Report — News/Calendars: Principles from the Reference Project

**Scope (read-only):** `fx-trading-system-main/src/fx_system/` — `cftc.py`, `cftc_release_calendar.py`, `central_bank_calendar.py`, `publication_calendar.py`.
**Audience:** A0 / Nexus audit swarm. Principles and data semantics only; no code reproduced.

## CFTC positioning ingestion and interpretation

The reference treats weekly CFTC Traders-in-Financial-Futures data as a *derived, lagged, and provenance-bound* artifact rather than a plain download. Every raw archive is recorded with its URL, byte size, SHA-256, retrieval timestamp, and cache/download status, and the final dataset carries a manifest so that any consumer can re-derive exactly what was ingested. Two distinct time semantics are kept separate on every row: the *observation* time (the report's as-of date, the week the positioning describes) and the *availability* time (when a conservative reader could actually have known it). Availability is modeled as a deliberately conservative, bounded lag applied to the observation date, and validation rejects any row where availability precedes observation — this is the point-in-time discipline that prevents hindsight leakage. Raw long/short columns are normalized into signed net ratios against open interest, which makes positioning comparable across contracts and across time; bounds checks, positivity checks on open interest, currency-code shape checks, and uniqueness on the currency/availability key reject silently corrupted input instead of propagating it. Interpretation semantics are explicit: a positive net ratio means long the foreign currency versus USD because the contracts are quoted that way, and each row is stamped with quality tags declaring that availability is *approximate-conservative* and that values are a *current revised historical archive*, not the as-published vintage. Overlapping archives (a multi-year history file versus per-year files) are de-duplicated by a declared priority so the freshest authoritative record wins deterministically. Atomic write-then-replace and a companion manifest with a CSV hash ensure a partially written file is never mistaken for a complete dataset.

## Central bank meeting calendars as announcement-risk controls

The central-bank calendar is explicitly framed as an *announcement-risk control, not a directional signal*, and the schema is built around that purpose. An eight-authority contract pins each authority to exactly one currency and one IANA timezone, so a row cannot silently claim the wrong zone or the wrong unit — timezone drift and currency mismatches are load-time errors, not runtime surprises. The most important semantic decision is that *timing quality is a separate field from the timestamp itself*. Five quality tiers distinguish an officially verified actual publication minute, an officially scheduled time, a time derived from a published standing rule, a date-only official source, and unverified external timing; formal experiments reject the unverified tier outright. Evidence and structure are cross-validated: a date-only row may not carry a publication minute, a rule-derived row must carry a rule identifier and an effective interval containing the event date, and rule metadata may not appear on any other tier. Event lifecycle is modeled with scheduled/unscheduled/cancelled/superseded statuses plus an explicit supersession pointer validated for same-authority and no-future-supersession constraints, so reschedules and cancellations are recorded history rather than overwritten rows. The cancelled flag and status must agree, and cancelled events may not claim a publication timestamp. Local-to-UTC conversion is strict about daylight-saving edge cases: a local wall time that does not exist or is ambiguous in the zone is rejected rather than guessed. Coverage is declared in the manifest, per-authority adapter completeness is checked with an optional fail-closed mode, and row counts per authority must reconcile with the calendar, giving a closed-world guarantee that "no events found" means genuinely none, not a broken adapter.

## Macro publication calendars and the ban on inference

The publication-calendar module encodes a single hard rule: *never infer an event date, weekday, or holiday — require an externally verified row*. Lookup by event name and local date either returns exactly one explicitly recorded row or raises; there is no weekday fallback, no business-day calendar consultation, and no synthesized "probably published" answer. The calendar must be non-empty and its header frozen, so a missing or schema-drifted file fails loudly at load. Each row carries a status that says whether the event actually happened (published, not published, or early), a quality flag, a source URL, and a retrieval timestamp, and formal mode rejects any unverified row. Status semantics interact with the recorded local time: the default scheduled clock time is required for a normal publication, while an earlier-than-default time must be tagged as early so that unusual but genuine releases are representable without loosening the schema. Coverage completeness is asserted per period — for a month-end benchmark fix, every calendar day of the month must have an explicit published/not-published row before a "last publication of the month" answer is allowed, and the chosen candidate must additionally be verified and published. This converts "which day was the fixing" from a calendar-math heuristic into a documented, auditable lookup. The actual event time is exposed only when the row says the event was published; a not-published row yields no event time at all, which prevents downstream code from treating a scheduled slot as a realized release. UTC conversion again refuses nonexistent or ambiguous local times.

## Release times, embargo, and the evidence hierarchy

The CFTC release calendar is the sharpest illustration of the *tentative schedule vs. actual publication* distinction. A planned release date from an annual schedule is evidence of intent, not proof of issuance; only an official source stating that an exceptional report was actually issued may set a "verified actual" flag, and the schema enforces that only one evidence category can ever claim that flag. Date evidence and time evidence are tracked as two independent axes: an announcement may establish an actual release *date* while stating no exact *minute*, and such a row must carry a date-only time-evidence label with an empty time field — it may not be padded with an invented clock time. The module's own documentation is explicit that a verified-actual row correctly returns no verified timestamp when the source never stated one. Consequently there are two accessors with different meanings: a *mapped* timestamp that reflects the best mapping but does not upgrade its own evidence quality, and a *verified-actual* timestamp available only when both date and time are substantiated. Lookups fail closed on unknown report dates instead of inventing the customary Friday release. Cross-field invariants (mapped release cannot precede the report date; only date-only evidence may lack a time; verified-actual implies date-only time evidence given current sources) mean a malformed or over-claiming row cannot load. Provenance closes the loop: every row cites a source id, URL, note, and retrieval time; retrieval after a declared knowledge cutoff is rejected as future information; and the manifest must contain the raw evidence file, its hash, a hash sidecar, and a catalog covering every id/URL the calendar references, with paths constrained to the manifest directory. This is the general recipe for embargo handling: a knowledge cutoff plus per-row retrieval times plus hash-verified raw evidence makes "was this knowable then?" a decidable question instead of a judgment call.

## Revision tracking and vintage semantics

Revisions are handled by acknowledging them rather than hiding them. The CFTC pipeline labels its value vintage as a *current revised historical archive, not an as-published vintage*, and labels availability quality as *approximate-conservative* — so a researcher knows the series is a later-restated view of an earlier week, and must not read it as what a trader saw on the original release day. When two sources supply the same observation, precedence is declared in advance (archive priority) and de-duplication is deterministic and keyed on the observation identity, never on row order. For the calendars, the analogous mechanism is supersession: a corrected or rescheduled event is a new row pointing at the event it replaces, with constraints that keep the chain sane (same authority, never superseding a later event), while cancellations remain visible records instead of deletions. Nothing is mutated in place — files are written to a temporary path and atomically replaced, and both the dataset and its manifest carry hashes so a consumer can verify that the bytes it reads are the bytes that were validated. The manifest records schema version, parser version, row count, coverage interval, adapter completeness, and the full source catalog, which turns any downstream discrepancy into a traceable question of which vintage and which parser produced it. The consistent principle across all four modules: quality metadata travels *with* the data as columns and attributes, not as prose in a README, so a downstream consumer cannot accidentally drop it.

## Scheduled-event risk controls (blackouts)

Blackout construction is deliberately asymmetric and conservative. For a timestamped event the interval is half-open — from release-minus-buffer to release-plus-buffer — with buffers that must be non-negative. For a date-only event the reference refuses to invent a publication minute and instead blackouts the *entire local civil day* in the authority's own timezone, expanded by the same buffers; the local-day boundary is what matters because "the ECB decides on Thursday" is a statement about Thursday in Berlin, not a UTC instant. Cancelled events yield no blackout interval at all (an error, not an empty interval that could be mistaken for "clear"), and events lacking a usable official time likewise error out rather than silently producing no window. Buffers are parameters of the risk policy, not properties of the data, so tightening or widening a window never requires touching the evidence. Because the calendar declares per-authority coverage and adapter completeness with fail-closed semantics, a coverage gap can be distinguished from a genuinely quiet week — the distinction that decides whether the system is safe to trade or should stand down. The overarching stance: scheduled-event risk control defaults to *stop* whenever the timing evidence, coverage, or provenance is insufficient, and only opens when the calendar affirmatively says it is safe.

## Key Principles for Nexus

- **Separate observation time from availability time on every fundamental row.** Store an `available_time` alongside the event/as-of time and reject any row where availability precedes observation; this is the cheapest guard against look-ahead leakage in `nexus-news` economic events.
- **Make timing evidence a typed field, not a comment.** Adopt a quality enum (verified-actual / official-scheduled / rule-derived / date-only / unverified) on calendar events, and forbid a date-only row from carrying a clock time — never invent an event minute to fill a schema.
- **Build blackout windows from evidence quality, and fail closed.** In `BlackoutEngine`, treat a date-only high/medium event as a full local-day blackout in the event's own IANA timezone, not a fabricated timestamp; treat cancelled events as "no window" and missing/unusable event times as a `degraded` (block) state, never as `clear`.
- **Declare coverage explicitly and distinguish "no events" from "no data".** Persist a coverage interval plus per-source adapter status/row counts; a coverage gap must surface as degraded/blocked, not as an empty calendar that reads as a quiet market.
- **Version the policy and hash the inputs.** Keep `policy_version` on every blackout decision, and record source URL, retrieval timestamp, raw-evidence SHA-256, and a knowledge cutoff for each calendar snapshot so "was this knowable then?" is answerable for audits and replays.
- **Model schedule changes as append-only supersession/cancellation records.** Rescheduled or cancelled economic/central-bank events become new rows referencing the event they replace (validated for ordering), so history stays auditable instead of being overwritten.
- **Derive signed, normalized features with declared bounds.** For positioning-style series, keep raw long/short plus open interest and publish signed net ratios with positivity/bounds/uniqueness validation and explicit vintage-quality tags (current-revised vs. as-published).
- **Refuse inference: exact-key lookup only for event calendars.** `event_on(name, date)`-style access must raise on missing rows rather than fall back to weekday/holiday heuristics, and full-period coverage must be asserted before answering "last event of the month" style questions.
